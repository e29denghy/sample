# GPT-6 Astra 发布：哪些工作值得重新交给它？

9 月 3 日，OpenAI 正式发布 GPT-6 Astra。前几天写《Fable 5.1 发布，AGI 要来了？先别急》时，Astra 还处在等待发布的阶段；现在，官方名称、API 型号和价格都已经明确。

读完发布说明、媒体报道和首批独立评测，我更愿意把这次更新理解为：**一些原本要人反复接手的电脑工作，开始值得重新交给模型试一遍。** 至于把所有请求都切到 Astra，现有证据还不支持这么做。它在编码代理上的效率提升很实在，综合知识任务的收益却没有同样整齐。

本文依据截至 2026 年 9 月 6 日可读取的公开资料。下面的实测均注明来源；本站没有完成自己的 Astra 对照测试。

## 先看它把哪些工作往前推了一步

过去评价模型，常常盯着回答是否正确。电脑操作多了一层麻烦：模型得找到正确窗口，理解页面状态，填写内容，等结果，再确认刚才的操作有没有生效。一次判断错了，后续步骤可能都建立在错误状态上。

OpenAI 这次把电脑操作放在发布说明的前面。它展示了 KiCad 电路板布局、文档排版、网页前端验收等任务。这些是官方挑选的演示，适合用来看能力方向，不能据此估计日常工作的成功率。[1]

比演示更有用的是带口径的数字。在官方公布的 OSWorld 2.0 离线子集、部分得分口径下，Astra 得到 72.6%，GPT-5.6 Sol 为 65.7%。官方的延迟模拟中，对应任务耗时约为 40 分钟和 75 分钟。这说明值得测试它在多步骤操作上的改进，但这里的“模拟”“离线子集”和“部分得分”都不能省略，更不能翻译成“现实电脑工作有 72.6% 可以完全自动完成”。[1]

终端任务的提升也很明显。OpenAI 报告的 Terminal-Bench 4.0 成绩是 Astra 57.9%、Sol 37.3%、Fable 5.1 55.8%。这类任务涉及软件工程、系统配置和数据分析，更接近开发者交给 Agent 的整段工作。官方在所示配置下还估算，Astra 每个任务的 API 成本比 Sol 低约 9%。[1]

这些结果有一个共同前提：模型是在具体工具环境和推理设置下运行的。官方注明，汇总分数采用各推理强度中的最高结果，研究环境或 API 的系统提示、工具也可能与 ChatGPT 产品不同。把模型名抄进自己的系统，并不会自动得到发布页上的成绩。

## 上手案例里，有比“一次生成成功”更有用的细节

Claire Vo 在 9 月 3 日的 How I AI 上手文章中，展示了 Astra 操作真实业务软件的过程。她让它修改节点式 CRM 工作流：根据线索分配结果生成邮件，把草稿送到 Slack 等待审阅。另一个案例是读取 Flora 中已有的图像处理流程，生成素材，再进入 Figma 组装节目缩略图。[5]

这些任务让我更关注它能否沿用现有工作，而非只会从空白页面开始。业务里有大量时间花在已有表单、已有模板和已有流程上。模型如果能理解这些上下文，减少的就是在人和软件之间来回搬运信息的时间。

她还记录了一次持续约 1 小时 45 分钟的浏览器 QA：模型打开预览分支，发送聊天、刷新页面、检查开发者控制台，找到了团队此前漏掉的问题。对于做 Web 应用的人，这个案例比生成一个漂亮首页更值得复现。[5]

不过，这篇文章是拿到早期访问权限的产品从业者写的上手体验，并非统一条件下的盲测。作者也说，产品情报功能经过几轮跟进才完成，3D 服装游戏仍有衣物表现不理想的地方，正式的模型对照测试留待后续。它提供了“可以试什么”的线索，尚不能回答“平均成功多少次”。

## 独立评测没有给出一个统一的赢家

Artificial Analysis 在 9 月 3 日发布的评测中，给出了两组很不一样的结论。[4]

在 Coding Agent Index 中，Codex 内的 Astra 得到 67 分，接近 Claude Code 中的 Opus 5 和 Fable 5；Fable 5.1 以 70 分领先。在 max 推理强度下，Astra 的 token 使用量约为 Sol 的三分之一，成本大致相同，得分高 2 分；相对同分的 Fable 5，每任务成本不到一半。

这是支持升级编码任务的直接证据。它同时比较了完成质量和资源消耗，比单看每百万 token 的报价更贴近实际账单。但比较对象包括 Codex、Claude Code 等不同运行环境，结果属于“模型加工具系统”的组合，不能全部归因于裸模型。

换到同篇文章的 Intelligence Index，Astra 与 Sol 都约为 61 分，比 Fable 5.1 低约 5 分。Astra 在 max 下减少约 10% 的输出 token，却因为价格上涨，**每任务成本比 Sol 高约 75%**。省 token 和省钱，在这里走向了不同的方向。

长任务也不是全面进步。AA-Briefcase 中，Astra 的分析质量提高，呈现质量下降；GDPval-AA v2 则出现约 80 Elo 的回落。这些指标测的工作集合不同，我不会把其中一项扩大成“办公能力全面领先”或“全面退步”。更有用的判断是：如果你的任务重分析、重多步执行，值得单独测；如果主要是成熟模板下的内容整理，旧模型可能仍然合适。

这里引用的是 9 月 3 日评测文章及其当时的指数口径。Artificial Analysis 随后已经发布 Intelligence Index v4.2 的介绍，旧文章里的 61 分不应拿去和更新后榜单的分数直接比较。[4]

## 价格高了，账要按完成一件事来算

OpenAI 公布的 Standard API 价格为每百万输入 token 10 美元、每百万输出 token 50 美元；缓存读写另行计费。API Fast 模式在可用条件下标称最高达到两倍速度，价格为 Standard 的两倍。它和 ChatGPT 订阅中的额度不是一张账单。[1]

举个仅用于说明报价的算例：假设一次任务有 10 万个普通、未缓存输入 token，以及 1 万个计费输出 token，Standard 模型费用为 1.50 美元。这个数还没有包含额外工具费用、失败重试和人工复核，也不是任何实测任务的报价。

真正接入时，我会看每个通过验收的任务花了多少钱：模型调用、工具调用、重试和返工都算进去。一个单价更高的模型，如果明显少走弯路，可能值得；如果只是把同样的短答案写得更快，差价未必能收回来。

可用范围也需要分开看。官方发布时先向有限组织开放，计划在随后几天覆盖 ChatGPT Plus、Pro、Business、Enterprise，以及 API、Azure 和 AWS Bedrock；Pro、Business、Enterprise 还列有 Astra Pro。Enterprise 默认关闭，需要管理员启用。这些是公布的开放安排，具体账户是否已经能用，应以账户实际权限为准。[1]

## “AGI 时代”的标题背后，媒体在追问什么

WIRED 的 Maxwell Zeff 和 The Verge 的 Hayden Field 都报道了 Greg Brockman 在发布简报中关于“AGI 时代”的判断。这个说法来自 OpenAI 高管，并不是两家媒体通过测试得出的认证结论。它们的这两篇文章属于发布报道，也没有给出记者自己的成套对照实测。[2][3]

我更关注报道中的另一个问题：能力提高之后，人还能否及时发现模型正在越界。WIRED 引述 OpenAI 首席科学家 Jakub Pachocki 的解释，随着能力增长，监控模型变得更困难；对监控缺乏足够信心，可能限制进一步扩展。The Verge 同样把安全措施和此前事件之后的信任问题放在报道中心。[2][3]

官方发布页并未回避这个矛盾。一方面，OpenAI 称 Astra 在授权边界与透明沟通方面有所改善；另一方面，在专门要求模型规避监控的测试中，其书面推理比 Sol 更难监控。某个内部测试里的零次越界，只说明这组测试的观察结果，不能替代生产权限控制。[1]

Astra 也达到 OpenAI 自身 Preparedness Framework 的网络安全 Critical 门槛。官方 ExploitBench 的 100% 来自关闭生产防护的能力评估；上线版本对漏洞利用概念验证等高级网络安全任务仍有限制。不能把研究环境的能力上限当成公开 API 的可用功能。[1]

对业务系统而言，这些信息应该落到执行设计上。检索资料失败可以换来源；数据库写入被拒绝，则必须保留中断状态和已经完成的步骤。官方说明，误对齐监控可能让正常工作变慢、暂停或停止，在 API 中任务会停止。应用需要知道任务停在哪里，不能把它当成普通网络超时，自动重复整段写操作。[1]

## 开发者升级时，先挑一段能验收的工作

我会先从一个已有失败记录、结果又容易检查的任务入手，例如在测试分支复现聊天页面的竞态问题，修复后用浏览器走完整个过程。保留原模型作为对照，使用相同起点和验收条件，记录完成率、耗时、账单与人工接手次数。这样的结果比继续收集排行榜更容易帮助自己做选择。

做教育产品也一样。可以先让模型依据给定教材整理一份有出处的课件草稿，检查内容与引用，再决定是否生成资源。不要把“找素材、改正式课程、对外发布”揉成一个无法检查中间结果的任务。Astra 的进步越集中在执行，任务分步后的验收就越有价值。

API 层面，这次有几项具体变化值得看：[6]

- 异步工具调用允许模型在工具执行期间继续处理独立工作；应用仍负责运行工具，并用原来的 `call_id` 交回结果。它适合检索、读取资料等并行步骤，不能消除任务之间本来就有的依赖。
- WebSocket 中途追加指令，可以在任务进行时补充限制、纠正需求，并在继续执行时保留已完成工作。界面也需要展示哪些步骤已经执行，方便用户判断补充要求会影响哪里。
- `configuration_update` 允许在对话中调整推理强度并保留缓存前缀。简单跟进和难题可以采用不同设置，但要核对文档中的兼容范围。

迁移并不只是改成 `model: gpt-6-astra`。官方指南明确：工具调用需要 Responses API；迁移时应移除 `temperature`、`top_p` 等不支持的参数；此前使用 `none` 或 `minimal` 的请求，建议从 `low` 开始比较。使用 EU 数据驻留的 Astra 请求暂不支持 Fast 模式。[6]

还有一个很贴近本站写作规则的细节：官方承认 Astra 仍倾向于详细、格式化的回复，也可能重复使用固定表达；它还可能过度澄清、过度测试。模型变强，不会自动让文章更像作者本人，也不会自动知道一个小修复应该做到哪里为止。现有的素材、语气要求、完成条件，仍然要给清楚。

目前最值得带走的结论，是把那些被旧模型卡住的多步骤工作重新拿出来试。先完成一次带成本记录的验收，再决定扩大多少使用范围。对于我关心的 AI 应用和 Web 系统，这会比先回答“AGI 到没到”更快产生实际结果。
